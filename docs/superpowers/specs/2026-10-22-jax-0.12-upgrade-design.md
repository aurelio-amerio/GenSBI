# JAX 0.12 compatibility upgrade — design

Date: 2026-10-22. Branch: `jax-0.12` (worktree `../GenSBI-jax-0.12`, off `main` @ 8653d33).

## Intent

JAX 0.12 is out. GenSBI currently declares `jax>=0.10.2,<0.12.0` and is locked at 0.11.0.
Past minor bumps (0.10 → 0.11) broke functions, and some deps (diffrax, numpyro, flax,
orbax) lag new JAX minors. We want to find out, in a controlled way, whether GenSBI and its
dependency stack work on 0.12, fix what breaks or is deprecated in our own code, and then
publish a widened compatibility range together with a new GenSBI release.

This is routine hygiene, not a response to a reported breakage. The policy going forward is
that the latest GenSBI release supports the current and the previous JAX minor at minimum
(here: 0.11 and 0.12), so users are never forced onto the newest JAX.

## Goals

1. Establish, with test evidence, whether GenSBI works on JAX 0.12 with a freshly resolved
   dependency stack.
2. Fix deprecation warnings and breakages that originate in GenSBI's own source.
3. Determine the lowest JAX version that still passes, by re-testing the declared floor
   (0.10.2) and the midpoint (latest 0.11.x) after the 0.12 work.
4. Publish the widened range in `pyproject.toml` with the right version bump (see
   "Versioning rule").
5. Confirm sbibm-jax and heal-swin-nnx (GenSBI's own sibling deps, both with no JAX ceiling)
   also run on 0.12, and patch them only if they actually break or deprecate.

## Non-goals

- Adopting new JAX 0.12 features or refactoring beyond what the upgrade requires.
- Working around deprecation warnings that originate inside third-party deps.
- Bumping unrelated dependency floors (numpy, flax, ...) unless the JAX upgrade forces it
  through resolution.
- GPU validation. CPU tiers and docs are the gate here; the GPU sanity run is the owner's
  step after the branch is ready, as usual.
- Changing the `extraslow` tier's exclusion from CI.

## Anti-goals (what would make this a failure even if it "works")

- Touching `main`'s working tree, `.venv`, `uv.lock` or the `gensbi` mamba env. All work
  happens in the worktree with its own fresh venv.
- Shipping a range we have not actually tested at both ends.
- Shipping with `[tool.uv] override-dependencies` or any other trick that hides a dep's own
  JAX ceiling. If a dep declares `jax<0.12`, users cannot install the combination, so GenSBI
  cannot claim 0.12 support until that dep releases. Overrides may be used for *diagnosis*
  only (to learn whether the dep's ceiling is real or conservative) and never committed.
- Silently narrowing the suite (skipping tiers, deselecting failing tests) to get green.

## Constraints

- Python 3.12, as in CI. All test runs use `JAX_PLATFORMS=cpu` (already set via pytest-env).
- CI tiers are the definition of "green": `not slow and not experimental and not extraslow`,
  then `slow`, then `experimental`, plus the Sphinx docs build (`uv sync --group docs`,
  `make html` in `docs/`). Lint (`flake8 --select=E9,F63,F7,F82`) must also pass.
- sbibm-jax and heal-swin-nnx are installed from their sibling checkouts
  (`../sbibm-jax` @ 6ffe721, `../HEAL-SWIN-nnx` @ de33b81), editable, so their tests can be
  run against the same resolved stack. Their torch / HF / jaxhp / pypesto extras are out of
  scope; only the JAX-dependent portions of their suites matter.
- The "strict" probe means `jax==0.12.<latest patch>` pinned exactly, letting uv resolve
  everything else fresh. The same applies to the 0.11 and 0.10.2 floor probes.

## Versioning rule (decided by the owner)

After the 0.12 work is green:

1. Re-run the full CPU gate with `jax==<latest 0.11.x>`.
2. Re-run it with `jax==0.10.2`.
3. If 0.10.2 still passes: range becomes `>=0.10.2,<0.13`, GenSBI ships as **0.4.3** (patch;
   existing user code does not break).
4. If 0.10.2 fails (including "uv cannot resolve 0.10.2 with the deps' own floors") but
   0.11.x passes: range becomes `>=0.11.<lowest passing patch>,<0.13`, GenSBI ships as
   **0.5.0** (minor; floor raised).
5. If 0.11.x also fails, that violates the "current + previous minor" policy. Do not pick a
   floor unilaterally: report what breaks on 0.11 and whether it is fixable in our code
   (e.g. a compat shim) and let the owner decide.

The same range must be applied in all four places in `pyproject.toml`: `dependencies`,
`cuda12`, `cuda13`, `tpu`.

## Deprecation policy

- Run the tiers with deprecation warnings surfaced (e.g. `-W always::DeprecationWarning`,
  `-ra`) and classify each warning by where its stack points.
- Warnings pointing into `src/gensbi` (or into sbibm-jax / heal-swin-nnx source) are fixed
  in that repo, using the replacement JAX recommends. A fix must keep the lower end of the
  final range working: prefer replacements available since the chosen floor; if none exists,
  a small version-guarded shim is acceptable.
- Warnings pointing into third-party deps are listed in the final report with the dep and
  message, and otherwise ignored.
- Pre-existing `FutureWarning`/`DeprecationWarning` that are unrelated to JAX (e.g. from
  sklearn or matplotlib) are out of scope; note them if cheap, do not chase them.

## Plan of work (what the owner decided, in order)

1. **Isolation.** Worktree `../GenSBI-jax-0.12` on branch `jax-0.12` (done). Create a fresh
   uv venv inside it. Nothing in this branch's env or lock is shared with `main`.
2. **Strict 0.12 probe.** Pin `jax==0.12.x` in the worktree's `pyproject.toml`, `uv sync`
   with the `test` and `docs` groups, install the two sibling repos editable. Record whether
   resolution succeeds and which deps moved (flax, orbax, diffrax, equinox, numpyro, optax,
   blackjax, grain, safetensors versions before/after).
   - Resolution failure caused by a dep's JAX ceiling → stop, report the blocking dep and its
     tracker/release status. Optionally diagnose with a non-committed override.
3. **Gate at 0.12.** Lint, three test tiers, docs build; then sbibm-jax and heal-swin-nnx
   test suites against the same env. Collect failures and deprecation warnings.
4. **Fix.** Address failures and in-repo deprecations (GenSBI first; siblings only where
   affected). Each fix is a focused commit. Re-run the affected tier(s) until green.
5. **Floor matrix.** Repeat resolve + gate with `jax==<latest 0.11.x>` and `jax==0.10.2`
   (fresh resolve each time; a new venv per probe is fine). Apply the versioning rule.
6. **Finalize.** Set the four ranges, bump `version` in `pyproject.toml`, regenerate the
   worktree's `uv.lock` (gitignored, but keep it consistent for local use), update any
   README/docs text that states supported JAX versions. For the siblings: pyproject touch and
   patch version bump only if their code changed.
7. **Report.** A short compatibility matrix (jax version × tier × result) and the list of
   dep-internal deprecations, in the branch's PR description and in the final summary to the
   owner. Hand-off: PR-ready branch; GPU sanity run, merge and release are the owner's.

## Left to the builder

- Exact uv invocations, how to swap the pin between probes, and whether to use one venv
  re-synced or one venv per probe.
- How to run the sibling suites (from inside the GenSBI venv vs. their own worktrees), as
  long as they run against the same resolved JAX.
- Mechanism for collecting and classifying warnings.
- Whether to diagnose a blocking dep ceiling with an override, and how to phrase the
  blocker report.
- Order and granularity of fix commits.

## Notes for the builder

- `uv.lock` is gitignored in this repo; version ranges in `pyproject.toml` are the source of
  truth for users. Do not try to commit the lock.
- Historically, `.venv` on `main` sometimes hid test failures that the mamba `gensbi` env
  surfaced (cause unknown). A fresh venv per probe avoids stale state; if results look
  suspiciously clean compared to history, re-check the env is what you think it is
  (`uv run python -c "import jax; print(jax.__version__, jax.__file__)"`).
- The `extraslow` tier is excluded from CI and from this gate.
