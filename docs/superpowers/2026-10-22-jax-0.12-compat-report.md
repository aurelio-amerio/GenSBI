## Blockers

### grain 0.2.18 `mp_prefetch` + jaxlib extension ≥ 448 → `absl.flags.UnparsedFlagAccessError` (dep-internal, sbibm-jax only)

**What fails.** Three sbibm-jax tests, all of which drive grain's `mp_prefetch` (multiprocess prefetch):

- `tests/data/test_dataset.py::TestLoaders::test_prefetching_loader_iterates`
- `tests/data/test_online_dataset.py::TestMultiprocessSmoke::test_one_worker_end_to_end`
- `tests/data/test_online_dataset.py::TestMultiprocessSmokeGRF::test_one_worker_image_end_to_end`

First traceback line inside the dep (deepest frame):
`site-packages/absl/flags/_flagvalues.py:544: UnparsedFlagAccessError: Trying to access flag --grain_enable_multiprocess_worker_profiling before flags were parsed.`
reached from `grain/_src/python/dataset/transformations/process_prefetch.py:173` → `grain/_src/core/profiler.py:69` (`is_worker_profiling_enabled`).

**Root cause (verified by reading grain 0.2.18 and A/B runs).** `grain/_src/core/profiler.py` imports
`jax._src.lib.jaxlib_extension_version` and, when it is ≥ 448, sets `_subprocess_hooks_loaded = True`.
Only then does `is_worker_profiling_enabled()` read the absl flag `--grain_enable_multiprocess_worker_profiling`.
In any process that never calls `absl.app.run()` (pytest, plain scripts, notebooks) absl raises
`UnparsedFlagAccessError` on that read. Extension versions measured here: jax 0.12.0.1 → 505,
jax 0.11.2 → 495. grain's own log message says the threshold corresponds to "jaxlib >= 0.11.0".

- It is **not a JAX 0.12 regression**: the same test fails identically in the 0.11.2 probe env.
  It is latent on `main`'s current lock (jax 0.11.0, grain 0.2.18). The sibling suite passed historically
  in the mamba `gensbi` env because that env has jax 0.10.2 (extension < 448) and absl 2.3.0.
- absl-py version is irrelevant: A/B at absl 2.5.1 / 2.5.0 / 2.3.0 in the 0.12 env all fail. Env restored to 2.5.1.
- **Fixed upstream, unreleased.** grain `main` wraps the read in
  `try: ... except flags.UnparsedFlagAccessError: return <flag>.default`. Latest PyPI release is 0.2.18
  (2026-06-17); no newer release exists as of 2026-10-22.
- GenSBI itself is unaffected: `src/gensbi` does not call `mp_prefetch` (all GenSBI tiers green at 0.12).
  heal-swin-nnx is unaffected.

**Options for the owner** (per spec, a workaround for a dep-internal break needs owner approval):

1. Patch sbibm-jax (`src/sbibm_jax/data/dataset.py`, before `mp_prefetch`): if `absl.flags.FLAGS` is not
   parsed, mark the single grain flag as present / call `FLAGS.mark_as_parsed()`, so grain reads its default.
   One-liner, works on 0.11 and 0.12, becomes a no-op once grain releases the upstream fix. Requires
   sbibm-jax 0.1.5 and raising GenSBI's floor (release order: sbibm-jax first).
2. Wait for grain > 0.2.18 and floor it. Unknown date.
3. Accept the three sbibm-jax failures as known (mp_prefetch path only) and ship GenSBI 0.5.0 anyway,
   documenting it. Users calling `TaskDataset(use_prefetching=True)` under pytest/scripts hit the error.

Per the plan's stop rule the plan halted after Task 3; Task 5's probes were still run (owner-independent evidence).

## Floor decision

GenSBI's own gate (lint, fast, slow, experimental, docs) and heal-swin-nnx pass at 0.11.1, 0.11.2 and 0.12.0.1.
**p = 1**: the shipped range would be `jax>=0.11.1, <0.13.0`. No dependency needed a lowered floor.

The only red cell in the matrix is sbibm-jax's `mp_prefetch` path, which fails identically at all three JAX
versions (grain 0.2.18 bug, see Blockers) and is therefore not a floor question.
